# Technical debt

What the code owes, so that shortcuts are taken on purpose and paid back in
order. Update it when an item is paid back or a new one is taken on.

Last audit: 2026-10-29, covering every crate, during milestone 3.

## Scoring

Each item is scored from 1 to 5 on three axes, as in Manguebyte:

- **Impact**: how much it hurts people using or extending MARÉ.
- **Risk**: how bad it is if it is never fixed.
- **Effort**: how hard the fix is.

`Priority = (Impact + Risk) × (6 − Effort)`. Higher goes first.

## Paid back

| # | Item | How |
|---|---|---|
| 12 | There was a C header for the layout but no C client library: connecting, the doorbells and the cycle were Rust-only | `mare-capi` builds `mareclient.dll` / `libmareclient.so` / `libmareclient.dylib` exporting `include/mare_client.h`, with a C++ layer in `include/mare_client.hpp`. Tests compile a C and a C++ client against them (Microsoft's compiler on Windows, gcc on Linux) and run each against a hub: 301 to 303 cycles, every input sample as the device recorded it, events delivered, structure sizes as Rust lays them out (2026-11-01) |
| 23 | `mare-drift` was built and tested on its own, not joined to devices: the hub ran one device, and nothing measured when each packet arrived, which the controller needs | A link (`mare_drift::link`) carries audio between two clocks with each packet's arrival time, and `mare_hub::aggregate` joins followers to a master device through two links each, every follower on its own thread. On fake devices 300 ppm fast and 500 ppm slow a sine crosses both ways at −103.5 dB RMS against where it came from, never starved, and neither side allocates (2026-11-01) |
| 21 | A client joining at 3 ms periods lost its first 10 to 150 ms (late once, then busy 3 to 47 times): the hub woke it while it was still connecting | Clients set a ready flag when they first wait, and the hub wakes only ready clients. On the Realtek in exclusive mode the start then had nothing late or busy, and the hub's longest wait fell from 2.2 to 2.7 ms to 0.18 ms (2026-10-29) |
| 6 | Objects were protected only by where they lived (the session's `Local\` namespace, the token's default access list, which also lets in SYSTEM and administrators) | Every mapping and event MARÉ creates on Windows now has a protected access list with one entry, allowing the current user; a test reads it back, and another shows a mapping with the default list read as not private (2026-10-29) |
| 10 | Checking whether every client had finished walked every awaited client after each wake: up to *n²* loads a cycle | The engine keeps the clients it woke in order and how many have finished, so each is checked until it finishes and not again; with a hundred clients one run's longest wait was 0.22 ms, against 1.3 to 4.1 ms before (2026-10-30) |
| 5 | On Unix a dead client was found with `kill(pid, 0)`, fooled by a zombie or a reused id | On Linux 5.3 and later the watch holds a `pidfd`, readable when the process ends, reaped or not; a test sees an unreaped child end. Other Unix systems (macOS) still check the id, and `ProcessWatch::is_exact` says so (2026-10-30) |
| 3 | CI existed only as a file, and macOS, Arm Linux and the minimum Rust version had never built MARÉ | The repository is public (github.com/alessonqueirozdev-hub/mare) and CI runs on every push: tests on Ubuntu x86 and Arm, Windows and macOS, format, lint and documentation on three systems, and Rust 1.85. Its first run failed only on documentation warnings, fixed in the next commit, which ran green (2026-10-30) |
| 14 | A client learned that its hub had gone only when a wait timed out (every 100 ms) | On Windows a client's waits also end on the hub's process handle: with the hub killed in a child process, the client returned `HubGone` in 3 to 6 ms over three runs. On Linux it still learns at its timeout (100 ms measured), as a futex cannot also wait on a process (2026-10-30) |
| 4 | The hub read a client's outputs through a plain slice of shared memory, a data race in Rust's model if the client kept writing after marking the cycle done | The hub reads each output sample with a volatile read: a client that keeps writing gives the mix wrong values and nothing worse (2026-10-30). It still writes an idle client's inputs through a slice; only the client could race that, and only by breaking the protocol in its own process |
| 2 | Doorbells on macOS polled their counter | They wait with `os_sync_wait_on_address` where it exists (macOS 14.4 and later, looked up at run time) and poll elsewhere; `Doorbell::wait_kind` says which, and a test requires `OsSync` on macOS, which CI's macOS runner passes (2026-10-30) |
| 18 | Shared mode refused to open without `IAudioClient3` (Windows 10 or later) | It falls back to `IAudioClient` at the engine's default period, which `OpenOptions::small_shared_periods = false` also asks for; an automated test plays silence that way on the Realtek (480-frame periods, 100 cycles in 1.000 s) (2026-10-30) |
| 7 | The housekeeper looked at the registry every 2 ms, 500 wakes a second for an idle hub | It has its own doorbell (layout 0.2, `keeper_bell`), which clients ring when they connect or leave and the engine rings when it lets a client go; between rings it sleeps for `HubConfig::housekeeping_interval` (20 ms by default, 50 wakes a second), which bounds how late a dead client is noticed. With the interval at 10 s a client was adopted in under 1.4 ms and freed at once on leaving (2026-10-30) |
| 11 | A client that died between claiming a slot and storing its process id left the slot claimed until the hub restarted | The housekeeper frees a slot claimed with no process id for longer than `CLAIM_GRACE` (1 s); a client that slow finds its next step refused. A test claims the only slot by hand and sees it freed under a new generation and taken by the next client (2026-10-30) |
